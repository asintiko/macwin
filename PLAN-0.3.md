# План MacWin 0.3: скорость, отзывчивость, Linux (Kali) и несколько устройств

Статус этапов — в этом файле и в [PROGRESS.md](PROGRESS.md). Обозначения: ✅ готово, 🔄 в работе, ⬜ не начато, 🧪 нужна проверка на реальных компьютерах.

## Откуда план

Версия 0.2 работает на реальных MacBook и Windows-ноутбуке, но ощущается «чуть медленной». Этот план сначала учит MacWin **измерять** задержку (без цифр оптимизация — гадание), затем убирает найденные причины по убыванию вклада, добавляет третью платформу — Linux, в первую очередь Kali, — и снимает ограничение «ровно два компьютера»: один основной и несколько вторичных, как в Universal Control (у Apple — до трёх устройств; у нас цель — до четырёх).

Что уже устроено правильно и менять не нужно (проверено по коду):

- Движения мыши идут **QUIC-датаграммами** «побеждает последняя» (`DatagramMsg::MouseAbs`, `engine/mod.rs`), а не по надёжному потоку, так что потеря пакета в Wi-Fi не тормозит курсор повторной передачей.
- Клавиши и кнопки — на отдельном потоке ввода с приоритетом выше буфера обмена и файлов (`INPUT_PRIORITY = 1`, `CLIPBOARD_PRIORITY = -1`, `FILES_PRIORITY = -2`), поэтому копирование большого файла не ставит ввод в очередь за ним.
- Захват ввода — на выделенных потоках (CGEventTap со своим `CFRunLoop` на macOS, низкоуровневые хуки со своим циклом сообщений на Windows), событие обрабатывается и отправляется сразу, без таймера-«тика» (тик 50 мс только для сердцебиения и аренды захвата).
- Собственный тап macOS переподключается после `kCGEventTapDisabledByTimeout`.

Значит, «медленно» — это, скорее всего, не очереди внутри MacWin, а одно или несколько из: сеть (Wi-Fi), ощущение скорости курсора (ускорение указателя), ограничение смещения у края экрана на Windows, задержка начала движения после простоя, скорость буфера обмена и переподключения. Этап 1 покажет, что именно.

### Этап 1. Измерение: цифры вместо ощущений

- Пинг внутри сеанса уже есть (`DatagramMsg::Ping/Pong`): считать по нему RTT и джиттер непрерывно и показывать в окне (вкладка **Диагностика**): RTT p50/p95, потери датаграмм (по `seq`), частота событий мыши, тип сети (Wi-Fi/Ethernet), версия партнёра.
- Метки времени по этапам внутри процесса: захват → движок → отправка; приём → инъекция. Гистограммы (`hdrhistogram`), раз в минуту в лог на уровне `debug`, в окне — текущие p95. Это «добавленная задержка MacWin» из таблицы целей.
- `macwin probe latency`: 30 с измерений с текстовым отчётом, который можно вставить в issue.
- Внешняя проверка: видео 240 к/с на телефон, где в кадре и мышь, и экран второго компьютера; считать кадры от движения руки до движения курсора (как делают при измерении задержки ввода). Методика — в `FIRST_RUN.md`.
- Готово, когда: по одному отчёту видно, где теряются миллисекунды — в сети, в MacWin или в ОС.

### Этап 2. Сеть

- **Wi-Fi экономит энергию между пакетами**: при простое радио засыпает, и первое движение после паузы приходит с задержкой 100 мс и больше. Пока курсор на втором компьютере, слать «пустые» датаграммы каждые 20–50 мс, чтобы радио не уснуло; в покое — нет (батарея). Проверить пользу измерением из этапа 1.
- **Приоритет пакетов ввода**: на macOS `SO_NET_SERVICE_TYPE = NET_SERVICE_TYPE_VO` на UDP-сокете (Wi-Fi WMM ставит такие кадры в очередь «голос»). На Windows `IP_TOS` система игнорирует — нужен qWAVE (`QOSAddSocketToFlow`, `QOSTrafficTypeVoice`); работает без прав администратора в локальной сети. На Linux — `SO_PRIORITY`/`IP_TOS` (DSCP EF).
- **Частота датаграмм**: мышь на 1000 Гц даёт 1000 пакетов/с; для Wi-Fi это лишняя борьба за эфир. Объединять движения в один пакет не чаще частоты кадров экрана партнёра (120–144 Гц → ≤ 8 мс), всегда отправляя последнее положение. Настройка, по умолчанию включена при высокой частоте.
- **quinn**: сейчас только `max_idle_timeout = 10 с`, `keep_alive = 1 с`; по умолчанию `initial_rtt = 333 мс` и Cubic. Задать `initial_rtt` для LAN (например, 10 мс), проверить влияние пейсинга на одиночные датаграммы, убедиться, что буфер отправки датаграмм не копит старые положения при заторе (отправлять только последнее положение из своего буфера, а не из буфера quinn).
- Инструкция пользователю (в `FIRST_RUN.md`, без изменений кода): оба компьютера в 5 ГГц или по кабелю; на Windows выключить энергосбережение адаптера Wi-Fi («Разрешить отключение этого устройства для экономии энергии»); не держать VPN на этих компьютерах; роутер с WMM.
- Готово, когда: p95 RTT и джиттер из этапа 1 по Wi-Fi 5 ГГц ≤ 20 мс и нет пауз на старте движения.

### Этап 3. Курсор

- **Ускорение указателя**. Сейчас партнёру отправляется абсолютное положение, вычисленное из смещения, уже ускоренного ОС источника (на Mac — поля `kCGMouseEventDeltaX/Y`, на Windows — `pt − park`), с поправкой только на масштаб экранов. Ускорение целевой ОС не применяется, кривые Apple и Windows разные — отсюда ощущение «не той» скорости. Сделать: регулятор «Скорость курсора на втором компьютере» (×0,5…×3) в настройках; затем — опция передавать **сырые** смещения устройства (Raw Input на Windows, на macOS — `kCGMouseEventDeltaX/Y` до ускорения недоступны, поэтому там останется ускоренное смещение) и применять одну общую кривую ускорения на стороне MacWin.
- **Край экрана на Windows**. `WH_MOUSE_LL` отдаёт положение курсора, которое Windows уже прижала к краю рабочего стола: припаркованный у края курсор не может «уехать» дальше, и быстрые движения в сторону края обрезаются — курсор на Mac кажется медленным именно в этом направлении. Решение: читать движение из **Raw Input** (`WM_INPUT`, `RIDEV_INPUTSINK`) — это смещения самого устройства без обрезки и без ускорения; хук оставить только для подавления событий.
- **Переход через край**. На macOS курсор отвязан от мыши (`CGAssociateMouseAndMouseCursorPosition(false)`), а не телепортируется каждый кадр — это правильно и совпадает с тем, к чему в 2026 году пришёл Deskflow. Проверить измерением, нет ли паузы 250 мс из-за интервала подавления локальных событий после `CGWarpMouseCursorPosition` при возврате (`CGEventSourceSetLocalEventsSuppressionInterval` → 0).
- **Прокрутка**: сверить ощущение плавной прокрутки трекпада Mac на Windows и колеса Windows на Mac; при необходимости — коэффициент.
- Готово, когда: пользователь не отличает скорость курсора на двух экранах, а у края нет «вязкости».

### Этап 4. Платформы

- macOS: убедиться, что поток тапа и поток инъекции получают приоритет `QOS_CLASS_USER_INTERACTIVE`; инъекция движения — `CGEventPost` в `kCGHIDEventTap` (сравнить с `kCGSessionEventTap` по задержке); не создавать объекты на каждое событие там, где можно переиспользовать.
- Windows: поток хуков — `THREAD_PRIORITY_TIME_CRITICAL` или MMCSS; разрешение системного таймера 1 мс (`timeBeginPeriod`) только пока идёт управление — все ожидания в tokio на Windows иначе округляются до ~15 мс; инъекция относительными `MOUSEEVENTF_MOVE` вместо абсолютных, чтобы работало «Повышенная точность указателя», если пользователь так настроил.
- Общее: горячий путь без аллокаций и форматирования строк; проверить, что `debug!` в нём отфильтрованы до форматирования; измерить по этапу 1 до и после.
- Готово, когда: добавленная задержка MacWin по этапу 1 укладывается в цель (p95 ≤ 5 мс) на обеих ОС.

### Этап 5. Буфер обмена и файлы

- Текст: на Windows перейти на событие `WM_CLIPBOARDUPDATE` вместо опроса; на macOS уведомлений нет — опрашивать `changeCount` каждые 100 мс, пока окно активно или идёт управление, иначе 250 мс.
- Картинки: кодирование PNG большого снимка экрана занимает секунды процессорного времени и задерживает всё остальное. Передавать сжатие на отдельный поток, кодировать быстрее (уровень сжатия ниже или другой формат внутри протокола), а для очень больших — объявлять «есть картинка» и передавать по запросу при вставке.
- Файлы: оставить передачу сразу при копировании, но ограничить скорость так, чтобы джиттер ввода (этап 1) не рос; при необходимости — отдельное QUIC-соединение для массовых данных.
- Готово, когда: текст появляется за ≤ 300 мс, копирование снимка экрана не вызывает пауз курсора.

### Этап 6. Соединение

- После сна: ловить пробуждение (macOS `NSWorkspaceDidWakeNotification`, Windows `WM_POWERBROADCAST`) и сразу переподключаться, не ждать `max_idle_timeout` 10 с и откат 1–10 с.
- Смена IP у партнёра: уже есть поиск в сети; сократить `DISCOVERY_WAIT` при наличии ответа, слать запрос сразу при ошибке подключения.
- Запуск: показывать окно до инициализации сети; измерить время от клика до окна.
- Готово, когда: после пробуждения оба компьютера «Подключено» за ≤ 2 с, запуск ≤ 1 с.

### Этап 7. Linux: Kali

Kali Linux ставится с Xfce, который работает на X11 («и это не изменится в ближайшее время» — документация Kali); GNOME в Kali с 2025.4 — только Wayland, KDE — Wayland по умолчанию с переключателем на X11 при входе. Проверка: `echo $XDG_SESSION_TYPE`. Поэтому порядок: сначала X11 (Kali Xfce), затем Wayland через порталы.

- **Крейт `macwin-platform-linux`** с теми же трейтами (захват, инъекция, экраны, буфер, трей, автозапуск, хранилище ключей):
  - X11: захват через XInput2 (`XI_RawMotion` даёт сырые смещения устройства без ускорения — лучше, чем на Windows; клавиши через `XI_RawKeyPress`), удержание курсора — `XIGrabDevice`/`XFixesHideCursor`, инъекция — XTest, экраны — RandR, буфер — X11 selections (`CLIPBOARD`, `TARGETS`, `image/png`, `text/uri-list`).
  - Wayland (GNOME, KDE): захват — портал `InputCapture` (барьеры на краях экрана — ровно наш сценарий), инъекция — портал `RemoteDesktop`, оба через libei; с версии порталов 1.21 сессии сохраняются, так что разрешение спрашивается один раз. Для wlroots-композиторов портал `InputCapture` пока не реализован — там только evdev/uinput.
  - Запасной путь для любого сеанса: evdev для захвата (`/dev/input/event*`) и uinput для инъекции; нужны udev-правило для `/dev/uinput` и группа `input`. На Kali пользователь по умолчанию в `sudo`, правило ставит пакет.
  - Трей: StatusNotifierItem (панель Xfce ≥ 4.16 и GNOME с расширением, KDE — встроено); автозапуск — `~/.config/autostart/macwin.desktop`; ключи — Secret Service (gnome-keyring/KWallet) с откатом на файл, который уже есть.
- **Пакет**: `.deb` для Kali/Debian (`macwin_0.3.0_amd64.deb`: бинарники, `.desktop`, иконка, udev-правило), сборка в CI на `ubuntu-24.04`, установка одной командой `curl … | sudo bash` или `sudo apt install ./macwin.deb`. Зависимости: `libxcb`, `libxi6`, `libxtst6`, `libxkbcommon0`, `libgl1`.
- **Оптимизация под Kali**: Kali часто живёт в виртуальной машине (VirtualBox/VMware) — там гостевые дополнения сами двигают курсор, и захват через evdev не видит мышь хоста; MacWin должен это распознать и подсказать режим «вторичный» через XTest/uinput. На ноутбуках с Kali: NetworkManager `wifi.powersave = 2` (выключить экономию Wi-Fi), в `.deb` — подсказка. Брандмауэра в Kali по умолчанию нет, порты UDP 47800/47801 открыты; если стоит `ufw`, установщик добавляет правила.
- Окно уже собирается под Linux (eframe с X11), в CI на Linux проходят все тесты; `macwin-ui` и ядро без изменений.
- Готово, когда: Kali Xfce (X11) работает основным и вторичным с MacBook и Windows с теми же показателями задержки, что и они; Wayland-сеансы GNOME/KDE — вторичным через порталы.

### Этап 8. Несколько устройств: один основной, до трёх вторичных

Сценарий: MacBook — основной; Windows-ноутбук слева, Kali — справа (или сверху). Курсор MacBook уходит на любой из них через свой край, клавиатура следует за курсором, буфер обмена общий на всех, файлы — тоже. Мышь любого вторичного может вернуть курсор на основной через тот же край. Между двумя вторичными курсор идёт через основной (как у Universal Control), напрямую — не в этой версии.

Что сейчас привязано к «ровно одному партнёру» (по коду):

- `config.toml`: один `peer` (`Config.peer: Option<PeerConfig>`) и одна расстановка `[arrangement]`.
- `macwin-core::layout::Layout { local, peer, map }` — одна карта «мои экраны ↔ экраны партнёра»; `arrange::resolve/scene` принимают одного партнёра.
- Движок: `Session.role = Idle | Controlling | Controlled` — одно состояние на весь процесс, без идентификатора партнёра.
- Сеть: `runner::run(opts.peer: Fingerprint)` — одно соединение с одним закреплённым отпечатком; `listen(addr, id, peer)` принимает только его.
- Окно: `UiState.peer`, `peer_screens`, `placement` — по одному.

Решения:

- **Топология — звезда.** Основной держит по соединению с каждым вторичным; вторичные между собой не соединяются. Все вторичные **слушают** (как сейчас), основной **звонит** всем. Это убирает вопрос «кто кому звонит» и держит одно место, где известна вся расстановка.
- **Конфигурация.** `peer` → `[[peers]]` (отпечаток, имя, ОС, адрес, собственная расстановка `placement` у каждого); старый файл с одним `peer` читается и сохраняется как список из одного. Расстановка — часть записи партнёра, а не глобальная.
- **Ядро.** `Layout` → `Desk`: мои экраны плюс список `(peer_id, экраны партнёра, PeerMap)`; переход через край выбирает партнёра по тому, какой из них соприкасается в этой точке; при наложении двух партнёров на один участок края — ошибка редактора, не рантайма. `Session.role` → `Controlling { peer_id, … } | Controlled { … }` (вторичный по-прежнему управляется ровно одним — основным). Одна `Pressed`-таблица нажатых клавиш на партнёра, чтобы при переходе с одного вторичного на другой клавиши отпускались там, где были нажаты.
- **Сеть.** `runner` → `Links`: по одному `run`-циклу на партнёра с собственным откатом и поиском в сети; `listen` принимает любой отпечаток из списка; события несут `peer_id`. Один UDP-порт на основном для всех, как и сейчас.
- **Буфер обмена.** Основной — узел: копия на любом устройстве рассылается всем остальным; версия `(clock, origin)` уже глобально упорядочивает обновления, так что это естественно расширяется с двух до N. Файлы передаются по запросу вставки (этап 5) — иначе копия на одном вторичном шла бы через основной на все остальные сразу.
- **Протокол.** Hello не меняется (каждое соединение по-прежнему «я и ты»); добавить в Hello список «других участников» (имя, ОС) только для отображения в окне вторичного. Версия протокола 1.4, старые клиенты поле пропускают.
- **Окно.** Редактор расстановки с несколькими прямоугольниками партнёров (перетаскивание каждого, запрет наложения на общий участок края), список устройств со статусом каждого, «Добавить компьютер…» запускает тот же мастер ввода кода. Вторичный видит, кто ещё в системе. Трей: статус по каждому устройству.
- **Ограничения версии.** До 4 устройств (1 + 3). Вторичный ↔ вторичный только через основной. Расстановку задаёт только основной.
- Готово, когда: MacBook управляет Windows и Kali через разные края, клавиатура и буфер следуют за курсором, обрыв связи с одним вторичным не трогает другого, а отключение одного из них не ломает расстановку остальных.

### Этап 9. Проверка на реальных компьютерах

MacBook + Windows + Kali: отчёт `macwin probe latency` до и после каждого этапа, видео 240 к/с для контрольной сквозной цифры, чек-лист из `FIRST_RUN.md` (дополненный Kali и третьим устройством). Результаты — в PROGRESS.md.

## Риски

- Приоритет пакетов (WMM/DSCP) зависит от роутера и драйверов; на Windows без qWAVE метка не ставится. Проверяется измерением, не обещается.
- Raw Input на Windows и сырые смещения на X11 меняют ощущение скорости — поэтому сначала регулятор скорости и измерение, потом смена источника смещений.
- Порталы Wayland: `InputCapture` есть в GNOME и KDE, но не во всех композиторах; поведение зависит от версий порталов.
- Виртуальные машины с Kali не дают настоящего захвата мыши хоста — честно сообщать об ограничении.
- Несколько устройств: расстановка с несколькими партнёрами усложняет редактор и переходы через углы; переход между двумя вторичными напрямую не делаем, чтобы не плодить соединения и состояния. Клавиши, нажатые на одном вторичном, при переходе на другой должны отпускаться — иначе «залипание».
